## Профили агентов, субагенты и кастомные лупы

**Цель:** не только «кодинг-режим», а **набор профилей** (`AgentProfile` / `RunMode`): свои system prompt, набор тулов, политика компрессии памяти, лимиты. Примеры: кодинг, исследование, строгий формат ответа, QA-гейт и т.д.

**Персистентная память:** общий долговременный слой. Главный агент при переключении в профиль или вызове субагента передаёт **срез** (бриф, релевантные observations, инструкции репо), а не весь сырой transcript. После работы — **структурированный итог** обратно в общую память (что сделано, файлы, открытые хвосты), без километров логов.

**Кастомные агент-лупы:** субагент или скилл объявляет **спецификацию цикла** — фазы (что разрешено), выход из фазы не по словам LLM, а по **валидаторам в коде** (JSON Schema, парсер формата, тесты, инварианты). При провале — повтор с ошибкой валидации, потолок итераций, опционально эскалация главному агенту. Для задач «точность и жёсткий формат» арбитр корректности — **код**, LLM только генерирует кандидат. Результат лупа: артефакт + метаданные (раунды, пройденные проверки).

**Кодинг как частный случай:** отдельный профиль (тулы read/grep/write/patch, мягче или иначе компрессия), плюс при необходимости луп с прогоном линтера/тестов как гейт.

**Референс по тулам/промптам:** разобрать [OpenCode](https://github.com/anomalyco/opencode) (`packages/opencode` — registry тулов, `session/prompt/*.txt`, compaction сессии).

## Выгрузка документа из памяти на диск

`get_document` сейчас возвращает текст в контекст агента. Альтернатива — сохранять документ в файл и отдавать путь. Полезно для больших документов, которые не нужно читать целиком прямо сейчас, но нужно передать в другой инструмент или отправить пользователю. Можно сделать параметром `save_to_file: bool` или отдельным инструментом `export_document`.

## Секретарь — отправка сообщений от имени пользователя

Агент пишет сообщения контактам пользователя в Telegram от его имени. Пользователь даёт поручение ("напиши Анне что опоздаю"), агент формулирует сообщение и отправляет через userbot (Telethon/Pyrogram) с аккаунта пользователя, не бота. Требует отдельной авторизации userbot-сессии. Нюанс: нужно подтверждение перед отправкой, чтобы агент не отправил что-то не то.

## Сжатие вывода инструментов в LogCompressor

Сейчас LogCompressor при наступлении `to_observe`-зоны скармливает всё подряд Observer-LLM — включая большие сырые ответы инструментов (100+ строк поисковой выдачи, результаты запросов и т.п.). Observer суммирует это в наблюдение, но теряет детали.

Идея: ввести промежуточный порог `pre_compress` между `recent` и `to_observe`. Тёрны инструментов в этой зоне не идут сразу в Observer, а сначала проходят отдельный шаг — ЛЛМ решает как их сжать, опираясь на свой фокус внимания:

- Агент вызывает `compress_result(tool_call_id, summary)` во время диалога, если хочет явно указать суть результата.
- Если агент не вызвал `compress_result` — механическое сжатие: превью + ссылка на оффлоадный файл.
- После `pre_compress`-обработки тёрны инструментов уже компактные и нормально проходят через Observer.

Это делает сжатие **attention-driven**: то что агент счёл важным — сохраняется точно, остальное — схлопывается. Реализуется как дополнительная зона в `LogCompressor`, не новый компрессор.

## Стриминг выволнения команд в докере
Проблема в том, что вывод может быть очень большой и сейчас агенту отдается ограниченное число строк, вопрос как это стримить в телеграм. Наверное телеграм выводит всегда последние строки не более 2000 символов, будто консоль работает внутри сообщения.

## Contentless FTS5 для facts_fts

Сейчас в [src/memory/providers/fact/storage.py](../src/memory/providers/fact/storage.py) виртуальная таблица `facts_fts` создана как обычный FTS5:

```sql
CREATE VIRTUAL TABLE facts_fts USING fts5(fact_id UNINDEXED, fact);
```

Текст факта дублируется: раз в `facts.fact`, раз в `facts_fts.fact`. На больших memory это лишние гигабайты.

Вариант — перейти на **contentless FTS5**:

```sql
CREATE VIRTUAL TABLE facts_fts USING fts5(fact, content='facts', content_rowid='rowid');
```

Индекс не хранит копию текста, при выдаче результатов достаёт его из `facts` по `rowid`. Экономия ~30-40% места. Миграция требует drop + recreate таблицы и триггеров. Не срочно — пока память небольшая, дублирование некритично.

Подсмотрено в prism-mcp (`lib/prism-mcp`), у них так сделано изначально.

## Объединить host↔container коммуникацию через один канал sandbox-proxy

Сейчас в SandboxSkill **два параллельных механизма** общения хоста с контейнером:

1. **Skill-скрипты** ([src/skills/sandbox/__init__.py](../src/skills/sandbox/__init__.py) `_dispatch_skill_script`): на каждый вызов `podman exec python /slonagent/runner.py <script>` — новый процесс, RPC через stdin/stdout (`container_lib/rpc.py` Channel). Богатый API host-объектов (transport, memory, agent), но cold-start ~150мс на каждый вызов.

2. **Sandbox-proxy** ([src/skills/sandbox/container_lib/sandbox_proxy.py](../src/skills/sandbox/container_lib/sandbox_proxy.py)): один долгоживущий процесс, WebSocket-тоннель, custom JSON frames (`http`, `ws_open`, `cgi`). Быстрый, но без RPC — только forwarding.

**Идея:** сделать sandbox-proxy единственным каналом. Добавить в его протокол `kind: "exec_script"` и поверх тоннеля прокинуть RPC (Channel в `rpc.py` уже принимает `readline/writeline` — адаптируется под frame-транспорт). Тогда:

- `_dispatch_skill_script` перестаёт спавнить процессы — шлёт frame в существующий тоннель, получает результат. ~150мс → ~15мс на вызов.
- CGI-скрипты (`/web/*.py`) бесплатно получают тот же rich `agent.<...>()` API, что и skill-скрипты, без отдельного shim.
- Один протокол, легче отлаживать; multiplexing по `id` уже есть.

**Цена:** sandbox_proxy.py распухает в ~3 раза (RPC-сервер + диспатч), нужно правильно мультиплексировать concurrent script-calls в одном тоннеле, риск тонких багов на разрыве тоннеля / падении скрипта.

Поэтапно: сначала добавить RPC-возможность как новый `kind` (CGI получает сразу), `_dispatch_skill_script` оставить как есть. Если стабильно работает — мигрировать skill-script на тот же тоннель, удалять старый код.

## Cron в multi-thread форке

CronSkill регистрируется как обычный skill, поэтому каждый Agent в форке (parent + uuid-треды) получает свой инстанс. CRON.json лежит в `memory_dir` (per-fork, не per-thread) — все инстансы тикают одновременно и читают/пишут один файл. Проблемы:

- **Гонка на запись.** Разные тред-агенты могут одновременно перезаписывать CRON.json при tick'е (удаление выполненной задачи, пересчёт `scheduled_at`).
- **N-кратный fire.** Когда задача наступает, ВСЕ работающие тред-агенты видят её → все вызывают `process_message` → задача отрабатывает столько раз, сколько активных тредов.
- **Потеря треда-источника.** Cron вызывает `self.agent.transport.process_message`, но `transport.on_message` сейчас привязан к currently-bound агенту (не к тому, кто scheduling сделал). Задача может прилететь не в тот тред, где её планировали.

Возможные решения: вынести cron tick в один глобальный фоновый task на форк (а не per-thread skill), хранить thread_id с задачей, диспатчить в нужного агента.
